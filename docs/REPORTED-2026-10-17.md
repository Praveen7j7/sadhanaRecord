## 1. "Please try again" opening a contact card  — a live failure

**Seen:** Admin → Batch → Devotee → Suraj Sahu's card. The screen is empty but for
the red banner "Please try again". The nav still works, so only that one request fails.

**What that message means.** It is the app's wording for an unexpected server error
(`INTERNAL`), not a refusal. A FORBIDDEN or NOT_FOUND would say so in plain words.
So something THREW while building that one devotee's card.

**Where to look.** `devotees.get` → `devoteesGet()` in `worker/src/devotees.js:75`.
Two candidates, both on data rather than on code:

* **line 83** — `finalScores(w, w.mark_used)` runs for every SUBMITTED week. A
  submission row whose `body`/`soul`/`seva` JSON is unreadable, or whose shape
  predates a rules change, would throw here and take the whole card with it.
* **line 84** — the attendance query builds `IN (?, ?, …)` from the eight weeks
  found. Harmless unless `weeks` contains a null `week_id`, which the UNION in
  lines 79–82 can produce if `missed_weeks` holds a row the submissions table
  does not.

**How to confirm (not yet done).** `wrangler tail sadhana-record-api --format pretty`
while opening that card; the thrown message is logged even though the devotee is
shown the friendly one (api.js keeps the detail in `_internal`). Then read his
`submissions` rows directly.

**Is it happening elsewhere?** NOT YET KNOWN — and worth answering before fixing.
The honest check is to call `devotees.get` for every devotee and count failures,
rather than reasoning from one case. If it is one bad row the fix is that row; if
it is a class of rows the fix is `finalScores` refusing to throw.

## 2. A superseded G-type id must stop being displayed

**Rule.** Once a legacy id (GP26-…, GSP…, KT…) is linked to a person's official
IYF id, the old one is history, not identity. It must not appear on screen as
though it were their id — not on the card, not in About, not anywhere a devotee
or a coordinator reads.

It stays in the record and keeps resolving (ADR: old ids resolve forever), so a
search for the old number still finds the person. The difference is between
*resolving* an id and *displaying* it.

**Where this bites today.** `ids.get` was changed on 16 Oct to return the person
record beside the registry row, and the card now leads with the current IYF id —
but the heading of the search result is still the id that was SEARCHED. The rule
above goes further: the old id should not be the headline at all once a current
one exists.

## 4. A class-batch coordinator must not delete accounts

> **SUPERSEDED 22 Oct 2026 by ADR 0011** (`docs/DECISIONS/0011-who-may-delete-accounts.md`). The head decided the
> opposite: the head **and class-batch coordinators** may delete (anonymise) their own devotees; **training
> coordinators never** may. Do not build from the paragraph below.

**Rule.** Deleting a devotee's account is not a class coordinator's to do. The
button is visible in a coordinator login today (`devotees.delete`, STAFF).

**The distinction the head drew:** class batches — SPS, DPS, BSS, BVS and the
Vedic levels — versus TRAINING batches (MTP and the like). A training-batch
coordinator may delete; a class-batch coordinator may not.

**What this needs before it can be built.** The app has no notion of a training
batch yet: `batches` has `level` and now `tracks`, and every batch is a class
batch. So this rule needs the training/class distinction to exist first, and the
head's answer on where MTP and its siblings live.

## 5. Sign-up must offer the Vedic batches that are running

**Rule.** When somebody creates an account, the batch list must include the VL-2
and VL-3 intakes that are currently open — not only SPS and the levels above it.

A VL-2 devotee is where the journey now starts in the app (VL-1 stays on
sheets), so a batch they cannot choose at sign-up is a batch they cannot join
without a coordinator moving them by hand afterwards.

**Only while an intake is open.** A closed intake keeps its devotees and takes
no new ones. `meta.get` was already changed on 16 Oct to drop closed batches
from the list it sends (`b.active && !b.closed_at`), so the groundwork is there
— what is unverified is whether the sign-up screen itself shows the Vedic ones
correctly, since no VL intake existed when that screen was last looked at.

**And when none is running:** the options should simply not appear, rather than
offering a batch nobody can join.

## 6. The notification should come from the app, not from Brave

**Seen:** a push arrives headed `Brave • sadhana-record.iyfdel…`, in the SILENT
tray, while MoneyManager and the other apps beside it show their own name and
icon and arrive normally.

**Why.** The TWA shell has no notification delegate, so web push is handled by
the browser that backs the Trusted Web Activity and is attributed to it. The
Android Browser Helper library has a service for exactly this
(`TrustedWebActivityService` / `NotificationDelegationService`): with it
declared, the notification is posted by `org.iyfdelhi.sadhana` and carries the
app's own name, icon and channel.

It is a **shell change**, so it needs a new AAB and a Play upload — unlike a web
change, which reaches every phone by itself. Version code 4.

**Worth checking at the same time:** the reminder currently lands under SILENT.
That is a notification-channel importance, which the delegated service lets the
app set; a daily sadhana reminder nobody sees is not doing its job.

## 7. Promotion criteria in the export filters

**The head:** the export's filter options, for coordinators and the admin,
should include the promotion criteria — *"so when we decide to promote someone
his data can be verified"*. A coordinator filters their own batches only; the
admin, everyone.

**This is an extension, not new machinery.** `exports.page` already takes a
`filters` object (today: week status, facilitator), already scopes a coordinator
to the batches they coordinate, and already logs what was exported. What is
missing is the criteria themselves.

The criteria are written up in `ETP-PLAN-NOTES.md` ("Who is qualifying…"), read
from the dashboard's `PROMOTION_RULES`:

| Route | Criteria |
|---|---|
| VL-2 → VL-3 | attendance ≥ 50% |
| VL-3 → SPS | attendance ≥ 50% **and** chanting ≥ 4 rounds |
| SPS → DPS | sadhana ≥ 80 · night stay ≥ 80% · class attendance ≥ 80 · chanting ≥ 8 · 4 principles = Yes |
| DPS → BSS/BVS | the same five with chanting ≥ 12 — on observation |

Every input is already a column this app owns, so the filter can be computed
rather than read from anywhere.

**The rule that must survive:** a missing number counts as **not yet**, never as
a pass. An export that quietly treats a blank as a pass would promote somebody
on evidence nobody has.

**Still needs the head** (same three as in the ETP notes): what attendance is a
percentage OF, the two different chanting windows, and whether DPS → BSS/BVS
stays observation-only.

## 9. The mock still opens attendance on Sunday for everyone

**Found by a peer session, 17 Oct 2026, and confirmed here.**

Commit `ee9fed4` moved the server's attendance gates onto each batch's own class
day. The MOCK was not moved with it: `frontend/src/lib/mockweeks.js:35` still
reads

    export const attendanceOpens = (w) => new Date(weekStart(w).getTime() + 6 * DAY);

and six call sites across `mockweeks.js` and `mockstaff.js` use it, three of
them printing "the Sunday class" in so many words.

**Why it matters more than a stale copy.** The browser checks run against the
mock, so a mock on the old rule makes 1,800 checks agree with each other and
disagree with the server. That is the failure mode the head named: *"build
everything wherever required in all routes so things remain in sync"*.

**Why it is not fixed in this pass.** The mock keeps `classDay` on the
MEMBERSHIP (`mockstaff.js:49`), while the server now keeps it on the BATCH
(migration 0051). Mirroring the server means moving that field in the mock's
fixtures and updating every reader — a change worth making deliberately, not
squeezed in beside the ETP work. An attempt during this session broke three
suites and was reverted.

**Until it is done:** the server is correct and the mock is not, so a weekday
class behaves rightly in the app and wrongly in the offline demo and the browser
checks. Nothing a devotee uses is affected, because no weekday batch exists yet.
