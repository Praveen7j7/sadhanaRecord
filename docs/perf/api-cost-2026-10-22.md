# Sadhana Record Worker — database cost of every API action

Measured 22 Oct 2026 on a read-only export of HEAD 7b7b53b (`scratchpad/head/worker`), by instrumenting `tests/harness.mjs`
(`COST_LOG`) and running the whole suite (`node tests/run-all.mjs`: 56 suites, 2,478 assertions, all green before and after
the instrumentation, with and without `COST_LOG`). Raw aggregates: `api-cost.json` next to this file; per-hop logs and scripts in `cost/`.

## How to read the numbers

- **hop** = one Worker→D1 round trip. A single `first()/all()/run()` is one hop; a `db.batch()` / `reads()` list is ONE hop whatever its length.
  *hops* below are the hops the reply waits for; *after-hops* are `waitUntil` work after the reply (the replies cache, run_log,
  the refusal counter, the hourly sliding session expiry — exactly the four `waitUntil` statements in `src/`).
- **stmts** = statements sent (a batch of 4 = 4 stmts, 1 hop). **rows read** = rows RETURNED to the Worker. D1 bills rows SCANNED,
  so a statement that full-scans a table is undercounted here; such statements are flagged from `EXPLAIN QUERY PLAN` (column *scans*).
- **rows written** = SQLite `changes` per write statement (same thing D1 bills).
- p50 / max are over the suite's calls of that action; a suite call is a small database (a handful of devotees), so these are the
  FIXED cost of the action. What grows with the batch is in the growth table (2,000 and 5,000 seeded devotees).
- CPU is not measured here (Node's SQLite is synchronous; see loadtest/ for Worker CPU).

## 1. Suite totals

- 3887 API calls over 56 suites; 150 of 150 registry actions called at least once; 146 called successfully at least once.
- A refusal (res.ok=false) costs 0–2 hops in the common case: 0 when the action/fields check fails, 1 (session+account join) when the token is bad,
  2 (that + the scopeReads batch) for FORBIDDEN / MUST_CHANGE_PASSWORD. Over 1,617 refused calls: p50 2 hops, p90 4, max 16 (a VALIDATION refusal deep inside a handler).
- "(direct)" rows are database use outside `call()`: scheduled jobs and tests touching `env.DB` directly (views, mirror, push, account-delete suites) — not API actions.

## 9. Findings (measured, not estimated)

1. **N+1 per member in the closing/eligibility screens.** `batches.closingPreview` is 1 hop per member (629 hops, 1,261 rows for a 625-member intake),
   `eligible.list` 2 hops per member (1,255 hops, 1,886 rows). Both are one `GROUP BY login` away from 4–6 hops. At 10 ms CPU per call these are also the
   likeliest to hit the CPU cap on a real batch.
2. **The phase boards and cards re-read reference rows per person.** `board.get` costs 11 hops per trainee (338 hops for 30) and, for the facilitators' board,
   2 hops per devotee of each facilitator on top (551 → 851 hops from 2k to 5k devotees). A single `card.get` is 24 hops, `card.of` 26: `measures` is read 3×,
   `phases` 3–4×, the enrolment row 3–4× inside one call (cardOf → phaseAverage → scoreOf each re-read them).
3. **`settings.get` is 13 hops and `settings.update` 26 for ~10 settings rows**: they read `SELECT value FROM settings WHERE key = ?` one key per hop,
   twice over in update — `oversight.js settingsView()` has its own `g(key)` that runs `one(db, …WHERE key = ?)` per key, awaited one after another, instead of the memoised `settings(db)` map every other action uses. One `SELECT key, value FROM settings` (14 rows, 1 hop) would replace 10–11 hops; settings.update calls settingsView twice (before and after the write).
4. **The hourly sliding-session write clears the per-call memo**, so every call that triggers it reads the full settings table twice (14 rows, +1 hop):
   visible as hop 2 and hop 5 in home.get, week.saveDay, fac.devotees, group.mark. `requestDb.prepare()` clears the memo on any non-SELECT, including this `waitUntil` UPDATE.
5. **Rows that grow with the batch by design** (one row per devotee, as the screens list everyone): `stats.batch` 1,084 → 2,334, `devotees.list` 608 → 1,483,
   `exports.page people/weeks/days` 270–520 → 645–1,270 (first page), `fac.devotees` 267 → 617 for 100 → 250 devotees, `ids.possibleDuplicates` reads the whole
   registry copy (2,010 → 5,010 rows). `leaders.list` for ONE batch reads every member of every batch of the same LEVEL (1,875 rows for 3 SPS batches × 625).
   `stats.all` is flat (193 rows at both sizes). `home.get`, `week.get`, `history.list`, `announcements.list`, `card.get`, `members.list` are flat.
6. **`journals.get` returns 581 rows at p50 (1,227 max) — the largest reader among devotee-facing actions**: lectures (324) + book_files (156) + books (76), fixed
   reference tables but paid on every call that does not pass a current `have` version.
